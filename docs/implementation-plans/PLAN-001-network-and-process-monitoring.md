1. **Cel:** dostarczać udokumentowane, ograniczone metadane połączeń i zdarzeń procesów, bez przechwytywania treści TLS ani blokowania.
2. **Stan obecny:** Engine pobiera natywne tabele IP Helper do 800 TCP połączeń i 200 lokalnych UDP endpointów, z PID/nazwą procesu gdy dostępne. Domyślnie wyłączony opt-in monitoring co 1 s porównuje baseline i lokalnie zapisuje do 100 nowych zewnętrznych `Established`/`SynSent` TCP oraz nowych lokalnych endpointów UDP jako metadane informacyjne. Pięciominutowy profil co 1 s zebrał 300 próbek: CPU silnika 0,182% łącznej mocy procesorów, working set 53,4–69,8 MiB, `collect` mediana 6 ms / maksimum 46,5 ms; zapisał kontrolowane połączenie i 17 zdarzeń TCP łącznie bez pominięć zmian w tej sesji. To profil jednej lokalnej sesji, nie gwarancja produkcyjna. Endpoint UDP nie dowodzi wysłania datagramu ani nie ujawnia celu zdalnego. SQLite v7 przechowuje sieciowy baseline; SQLite v8 przechowuje baseline procesów; v14 przechowuje flagę obcięcia snapshotu procesów, a v15 flagi obcięcia tabel TCP/UDP. Oba baseline'y są aktualizowane atomowo ze zdarzeniami. Restart nie powtarza alertów, a wznowienie procesów wykrywa różnice od ostatniej próbki. Podczas pauzy procesów PID/nazwy są nadal pobierane co około 1 s, baseline jest lokalnie aktualizowany, ale zdarzenia nie są tworzone; UI i diagnostyka informują o tym wprost. Wykluczone aplikacje nie są trwale zapisywane. Pauza/wyłączenie monitoringu sieci unieważnia baseline przed kolejnym opt-in. Procesy są deterministycznie sortowane po PID i ograniczone do 10 000; obcięta próbka nie generuje niepewnych zdarzeń startu/zniknięcia. Próbki sieci są sortowane deterministycznie; przy obcięciu monitor wstrzymuje alerty do kolejnej pełnej próbki i sygnalizuje ten stan.
3. **Braki:** krótkie połączenia/datagramy/procesy między próbkami i gwarantowany event stream. Start procesu zapisuje ścieżkę obrazu, SHA-256, status Authenticode i ewentualne dopasowanie do importowanego feedu lokalnego; inspekcja działa w kolejce limitowanej do 33 elementów (w tym jednej pracy w toku), obejmuje pliki do 256 MiB i wznawia oczekujące wpisy po restarcie. Dane te pozostają wyłącznie lokalne. Brak dopasowania do ograniczonego feedu nie potwierdza bezpieczeństwa. Kandydat v0.15.34 trwale zapisuje correlationId dla startu procesu i połączenia/endpointu z tego samego PID oraz nazwą w oknie 60 s; ID jest tylko korelacją czasową. Po restarcie silnika mapa aktywnych startów jest odtwarzana z lokalnych zdarzeń w oknie 60 s; pauza czyści mapę. Przy `SQLITE_FULL` transakcja zachowuje poprzedni zatwierdzony baseline, a żywy proces ponawia zdarzenie po odzyskaniu miejsca. Zmiany procesów pomiędzy próbkami i krótkie procesy nadal mogą zostać pominięte. WMI `Win32_ProcessStartTrace` zwróciło `Access denied`; ponowna próba subskrypcji `Register-WmiEvent` w Windows PowerShell 5.1 (2026-10-22) potwierdziła `ManagementException` z `ErrorCode=AccessDenied` przed uruchomieniem syntetycznego procesu, więc zdarzenia nie utworzono. Próba `logman create trace` dla providera `Microsoft-Windows-Kernel-Process` również zwróciła `Access denied`, mimo członkostwa bieżącego konta w `Performance Log Users`; nie uruchomiono sesji ETW ani nie zmieniono polityk systemowych.
4. **Decyzje:** zastosowano polling bez podnoszenia uprawnień jako jawny fallback. Na tej maszynie kernel ETW nie jest dostępny przy aktualnych prawach; Microsoft opisuje wymagania administratora/`Performance Log Users` dla sesji ETW oraz dodatkowe jawne uprawnienia do sesji SystemTraceProvider. Nie nadawać ich po cichu. Event-driven kolektor może być osobnym, świadomie skonfigurowanym wariantem z kontrolowanym ACL i fallbackiem. Nie używać TLS MITM/WFP ani nie podnosić uprawnień domyślnie.
5. **Zależności:** wspólny `SecurityEvent`, ograniczona kolejka, Windows 10/11 x64, testy w Windows; dostęp do sesji/providera ETW musi być jawnie przyznany i zweryfikowany. Zob. [ETW session control](https://learn.microsoft.com/en-us/windows/win32/etw/controlling-event-tracing-sessions) i [SystemTraceProvider permissions](https://learn.microsoft.com/en-us/windows/win32/etw/configuring-and-starting-a-systemtraceprovider-session).
6. **Etapy:** (a) prototyp kolektora i benchmark; (b) test mapowania PID na proces; (c) deduplikacja/limity; (d) polityka pause/retencji; (e) test utraty źródła i restartu.

8. **Prywatność:** wyłącznie IP/port/czas/PID/nazwa pliku w minimalnym zakresie; nie przechowywać payloadów/URL; lokalna retencja i jawny opt-in.
9. **Testy:** Windows IP Helper test sprawdza PID żywego TCP listenera i UDP endpointu. Test jednostkowy kolektora weryfikuje zapis nowego lokalnego UDP endpointu oraz zastrzeżenie, że nie dowodzi datagramu. IPC test potomka weryfikuje zdarzenie start/stop. Integracyjny test wstrzykuje 10 500 PID; kolektor ogranicza próbkę do 10 000 PID, zapis do 100 zdarzeń i poprawnie raportuje pominięcia. Testy niepełnych próbek procesów obejmują stabilny wybór, brak fałszywych zdarzeń, restart, stan metadanych bez różnic baseline'u i migrację v13→v14. Test sieci symuluje obcięcie TCP, zmianę zestawu, restart i pełną próbkę; osobny test czytnika sprawdza, że limity 800/200 wybierają te same wpisy po przetasowaniu wejścia i ustawiają osobne flagi obcięcia. Migracja v14→v15 zachowuje endpointy. Osobny test wymusza awarię źródła i weryfikuje odzyskanie. Test live tworzy kontrolowany listener na interfejsie nie-loopback i potwierdza zapis nowego połączenia po baseline. Test korelacji procesu/TCP potwierdza odbudowanie mapy po restarcie monitora i granicę 60 s. Profil TCP `scripts/benchmark-engine.cjs --duration=300 --interval-ms=1000 --tcp-monitor` zebrał 300 próbek: CPU silnika 0,182% łącznej mocy procesorów, working set 53,4 MiB na starcie / 69,8 MiB maksimum, `collect` mediana 6 ms / max 46,5 ms; observer pozostał aktywny, kontrolowane połączenie i 17 zdarzeń TCP zapisano bez pominiętych zmian w tej sesji. Starszy pięciominutowy profil co 5 s: CPU 0,056%, working set 45,2–57 MiB, mediana `collect` 5,6 ms / max 675,9 ms. To pomiary pojedynczych sesji lokalnych, nie gwarancje długotrwałe ani pomiar pod sztucznym obciążeniem.
10. **Akceptacja:** snapshot pokazuje protokół/adresy/PID/nazwę gdy można; próbkowanie procesów tworzy informacyjne start/stop z PID, respektuje pause/wykluczenia, ogranicza snapshot do 10 000 PID i zapis do 100 zmian oraz raportuje liczbę pominiętych; UI ujawnia ograniczenia; brak blokowania. Krótkie procesy mogą zostać pominięte.
