# PLAN-001 — monitoring sieci i procesów

1. **Cel:** dostarczać udokumentowane, ograniczone metadane połączeń i zdarzeń procesów, bez przechwytywania treści TLS ani blokowania.
2. **Stan obecny:** Engine pobiera natywne tabele IP Helper do 800 TCP połączeń i 200 lokalnych UDP endpointów, z PID/nazwą procesu gdy dostępne. UDP pozostaje ręcznym snapshotem. Oddzielny, domyślnie wyłączony monitoring TCP odpytuje tabelę co 10 s, porównuje baseline i lokalnie zapisuje do 100 nowych zewnętrznych `Established`/`SynSent` jako metadane informacyjne. Respektuje pauzę i wykluczenia. Procesy są próbkowane co 5 s i zapisują start/stop do 100 zmian. Kontrolowane testy potwierdzają mapowanie PID dla TCP/UDP, działanie opt-in TCP oraz start/stop procesu.
3. **Braki:** krótkie połączenia/datagramy/procesy między próbkami, gwarantowany event stream, ścieżka/podpis, reputacja, korelacja połączeń z procesowymi zdarzeniami, odporność/diagnostyka zalewu oraz długotrwały soak. Przy `SQLITE_FULL` obserwatorzy zachowują różnicę do ponowienia w pamięci procesu, ale restart przed odzyskaniem przestrzeni może utracić niewpisaną zmianę. WMI `Win32_ProcessStartTrace` zwróciło `Access denied` dla bieżącego konta.
4. **Decyzje:** zastosowano polling bez podnoszenia uprawnień jako jawny fallback. Event-driven ETW/WMI wymaga osobnej oceny dostępu, kompatybilności i skutków elevated service. Nie używać TLS MITM/WFP ani nie podnosić uprawnień domyślnie.
5. **Zależności:** wspólny `SecurityEvent`, ograniczona kolejka, Windows 10/11 x64, testy w Windows; uprawnienia ETW do potwierdzenia.
6. **Etapy:** (a) prototyp kolektora i benchmark; (b) test mapowania PID na proces; (c) deduplikacja/limity; (d) polityka pause/retencji; (e) test utraty źródła i restartu.
7. **Pliki:** `src/Sentinel.Engine/`, nowe `src/Sentinel.Core/Monitoring/`, testy `tests/Sentinel.Tests/`, IPC `desktop/electron/main.cjs`, UI `desktop/src/main.tsx`.
8. **Prywatność:** wyłącznie IP/port/czas/PID/nazwa pliku w minimalnym zakresie; nie przechowywać payloadów/URL; lokalna retencja i jawny opt-in.
9. **Testy:** Windows IP Helper test sprawdza PID żywego TCP listenera i UDP endpointu. IPC test potomka weryfikuje zdarzenie start/stop. Integracyjny test wstrzykuje 10 500 PID; kolektor ogranicza próbkę do 10 000 PID, zapis do 100 zdarzeń, rejestruje 9 900 pominiętych zmian, a po cyklu start/stop poprawnie raportuje 19 800 pominiętych łącznie. Osobny test wymusza awarię źródła i weryfikuje stan, brak fałszywych zdarzeń oraz odzyskanie. Test live tworzy kontrolowany listener na interfejsie nie-loopback i potwierdza, że opt-in TCP zapisuje nowe połączenie po próbkowaniu. Testy .NET: 155/155; Engine IPC, w tym test live, PASS. Benchmark `scripts/benchmark-engine.cjs` trwał 300 s: 257 PID, średnie CPU silnika 0,057% łącznej mocy logicznych procesorów, working set 43,4 MiB na starcie i 53,8 MiB maksimum, 60 próbek `collect` p50 5 ms / max 1 359,8 ms. To pojedyncza sesja, nie gwarancja wydajności ani test CPU pod sztucznym wysokim obciążeniem. Pozostaje osobny soak test ciągłego TCP.
10. **Akceptacja:** snapshot pokazuje protokół/adresy/PID/nazwę gdy można; próbkowanie procesów tworzy informacyjne start/stop z PID, respektuje pause/wykluczenia, ogranicza snapshot do 10 000 PID i zapis do 100 zmian oraz raportuje liczbę pominiętych; UI ujawnia ograniczenia; brak blokowania. Krótkie procesy mogą zostać pominięte.
11. **Ryzyka:** snapshoty mogą pominąć połączenia krótkie; ETW zależy od wersji i uprawnień; VPN/TLS ograniczają widoczność.
12. **Status:** `IN_PROGRESS` — natywny snapshot TCP/UDP, opt-in monitoring przyrostów TCP, polling procesów, limity, retry po `SQLITE_FULL` i testy awarii/odzyskania przechodzą kontrolowane testy. Monitoring TCP jest domyślnie wyłączony i może pominąć połączenia krótsze niż interwał. WMI event stream blokuje brak uprawnień bieżącego konta. Pozostają soak test, trwała kolejka zmian podczas restartu, korelacja z procesowymi zdarzeniami i obsługa krótkich zdarzeń.
