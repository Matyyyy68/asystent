# PLAN-011 — monitorowanie trwałości Windows

1. **Cel:** po osobnym, jawnym włączeniu wykrywać zmiany w rejestrze Run/RunOnce użytkownika i maszyny oraz folderach Startup, bez udawania pełnego monitoringu wszystkich mechanizmów trwałości Windows.
2. **Stan obecny:** Electron rejestruje własne uruchamianie z Windows przez `app.setLoginItemSettings`, lecz produkt nie obserwuje zmian innych wpisów. Audyt read-only 2026-10-22 potwierdził dostęp do HKCU `Run` (0 wpisów) oraz folderu Startup użytkownika (1 element); klucz `RunOnce` nie istniał. W tej sesji HKLM `Run` i `WOW6432Node\Run` były czytelne (3 i 8 wartości), a wspólny Startup zawierał 2 elementy. Nie odczytywano ani nie wypisywano nazw i komend wpisów. Dziennik `Microsoft-Windows-TaskScheduler/Operational` jest dostępny, ale wyłączony; usługa działa. `Get-ScheduledTask` zakończył się `CimException`, kategorią `PermissionDenied`, HRESULT `0x80041003`; `schtasks /query` nie uzyskał listy. Read-only COM `Schedule.Service.Connect()` zwrócił `Connected=True`, ale `GetFolder(root)` zakończył się `DirectoryNotFoundException` / `0x80070003`; nie odczytano zadań.
3. **Stan implementacji:** opt-in monitor działa dla HKCU/HKLM `Run`/`RunOnce` (widoki 32/64-bit) i bezpośrednich plików w Startup użytkownika oraz wspólnym Startup. Snapshot co najmniej co 30 s, trwały zredagowany baseline SQLite, cichy pierwszy baseline, maks. 256 elementów i 32 lokalne zdarzenia na próbkę. Delta jest zapisywana atomowo z lokalnym zdarzeniem, więc zmiany utrzymujące się przez restart są wykrywane. Zdarzenia nie przechowują komendy ani pełnej ścieżki i nie trafiają do Enterprise. UI wyjaśnia zakres i ograniczenie zmian dodanych, a następnie cofniętych podczas zamknięcia. Jedenaście testów jednostkowych przechodzi; Engine IPC sprawdził read-only baseline profilu bez zmiany systemu.
4. **Decyzje architektoniczne:** monitor pozostaje wyłączony domyślnie. Nie włączać kanałów Event Log ani nie zmieniać rejestru/polityk systemowych. Nie wymagać administratora; HKLM jest teraz objęty read-only, zadania systemowe pozostają poza zakresem z powodu odmowy uprawnień. Użyć wykrywania zmian lub ograniczonego polling'u z debounce i bazą, która nie wywołuje alertów dla stanu zastanego przy włączeniu.
5. **Zależności:** nowe pole ustawień w Engine/UI; bez dodatkowego pakietu; testy Windows mogą używać wstrzykiwanego źródła i tymczasowego katalogu, bez zapisu do prawdziwych kluczy rejestru.
6. **Etapy implementacji:**
   1. Zdefiniować niejawny, stabilny klucz porównawczy źródła/wartości i typowane rekordy snapshotu.
   2. Dodać czytniki HKCU/HKLM Run/RunOnce dla widoków rejestru 32/64-bit oraz user/common Startup, ograniczając liczbę wpisów i wstrzymując wnioskowanie przy błędzie źródła.
   3. Dodać opt-in ustawienie, cykl baseline → delta, pauzę, status diagnostyczny i bounded queue.
   4. Zastosować wyjaśnialne heurystyki dla ścieżek Temporary/Downloads/Public; zdarzenia mają być informacyjne, dopóki nie ma wiarygodnej reputacji.
   5. Zintegrować lokalne zdarzenia bez Enterprise sync; nie zapisywać surowej komendy, argumentów ani pełnej wartości rejestru.
   6. Dodać testy baseline, add/change/remove, duplikatów, pauzy, błędu źródła, limitu i redakcji, następnie Windows live read-only smoke.
   7. Zaktualizować UI, diagnostykę, changelog, macierz i ten plan po pełnym buildzie.
7. **Zmiany w plikach:** spodziewane `src/Sentinel.Engine/WindowsPersistenceSnapshotMonitor.cs`, `Program.cs`, ustawienia w `src/Sentinel.Core/Models.cs`, UI `desktop/src/main.tsx`, testy Engine, a jeśli trwały baseline okaże się potrzebny — `LocalStore.cs` i migracja SQLite; lista ma być aktualizowana po wdrożeniu.
8. **Bezpieczeństwo i prywatność:** tylko opt-in; źródła systemowe są odczytywane bez zapisu, komendy, argumenty i surowe wartości nie trafiają do bazy, diagnostyki, eksportu ani Enterprise. Najpierw ustanowić baseline, by istniejące aplikacje nie powodowały zalewu alertów. Nie uruchamiać ani nie zmieniać wskazanych plików/wartości.
9. **Testy:** źródło wstrzykiwane; kontrolowane wpisy syntetyczne; test ścieżek reparse point; limity wielkości/liczby; brak ujawnienia wartości w zdarzeniu i eksporcie; testy włącz/wyłącz/pauza; migracja v19→v20 i backup/restore; Windows IPC read-only. Nie testować zmian w prawdziwym HKCU/HKLM.
10. **Kryteria akceptacji:** domyślnie wyłączone; baseline bez zdarzeń; zmiana syntetyczna tworzy jeden lokalny rekord; wyłączenie/pauza zatrzymuje obserwację; odmowa/awaria źródła jest diagnozowalna; surowa komenda nie jest zapisywana/eksportowana/synchronizowana; ograniczenie Scheduled Tasks jest widoczne w UI/dokumentacji.
11. **Ryzyka i ograniczenia:** nie obejmuje usług, sterowników, WMI/COM, zadań zaplanowanych, polityk logowania ani wszystkich ścieżek `Run`; polling może pominąć krótkotrwałe wpisy; ścieżki mogą być aliasowane przez zmienne środowiskowe/reparse points; heuristiczne lokalizacje mogą dać false positives.
12. **Status realizacji:** `IN_PROGRESS` — czytniki, baseline, delta, UI i testy wdrożone; testy monitora 11/11 oraz pełna bramka SQLite v20 PASS (.NET 245/245 bez pominięć, Engine IPC, UI i installer self-test). Nie przetestowano zmiany rzeczywistego wpisu autostartu ani Scheduled Tasks; nie wykrywa zmian dodanych i cofniętych w całości podczas zamknięcia aplikacji.
