# PLAN-011 — monitorowanie trwałości Windows

1. **Cel:** po osobnym, jawnym włączeniu wykrywać zmiany w rejestrze Run/RunOnce, Policies Explorer Run i wartości Winlogon Shell/Userinit użytkownika oraz maszyny, folderach Startup, zaplanowanych zadaniach oraz konfiguracji usług i sterowników Windows, bez udawania pełnego monitoringu wszystkich mechanizmów trwałości.
2. **Stan obecny:** Electron rejestruje własne uruchamianie z Windows przez `app.setLoginItemSettings`. Audyt read-only 2026-10-22 potwierdził dostęp do HKCU `Run` (0 wpisów), HKLM `Run` i `WOW6432Node\Run` (3 i 8 wartości) oraz user/common Startup (1 i 2 elementy); nie odczytywano ani nie wypisywano nazw ani komend. Pierwotne WMI i COM były niedostępne w ograniczonym środowisku. Późniejszy odczyt poza sandboxem przez `schtasks /query /xml` bez uruchamiania zadań poprawnie sparsował 175 wpisów; standardowy sandbox zwrócił kod 1. Dziennik Task Scheduler pozostaje wyłączony i nie był modyfikowany.
3. **Braki:** nie są monitorowane AppInit_DLLs, rozszerzenia powłoki, WMI subscriptions ani inne mechanizmy poza wymienionymi źródłami. Polling co ≥30 s może przeoczyć wpis dodany i usunięty pomiędzy próbkami. Kanał Task Scheduler Operational pozostaje wyłączony i nie dostarcza historii zdarzeń; `schtasks` może odmówić dostępu, a wtedy zmiany zadań nie są widoczne do czasu odzyskania dostępu. To świadome ograniczenie zakresu opt-in monitora, nie pełny audyt wszystkich mechanizmów autostartu Windows.
4. **Decyzje architektoniczne:** monitor pozostaje wyłączony domyślnie. Nie włączać kanałów Event Log ani nie zmieniać rejestru/polityk/zadań systemowych. Odczyt zadań jest best-effort: standardowy proces może otrzymać odmowę; UI pokazuje stan, zachowuje baseline i kontynuuje pozostałe źródła. Użyć ograniczonego polling'u i cichego baseline'u, aby nie tworzyć alertów dla stanu zastanego przy włączeniu.
5. **Zależności:** nowe pole ustawień w Engine/UI; bez dodatkowego pakietu; testy Windows mogą używać wstrzykiwanego źródła i tymczasowego katalogu, bez zapisu do prawdziwych kluczy rejestru.
6. **Etapy implementacji:**
   1. Zdefiniować niejawny, stabilny klucz porównawczy źródła/wartości i typowane rekordy snapshotu.
   2. Dodać czytniki HKCU/HKLM Run/RunOnce/Policies Explorer Run oraz Winlogon Shell/Userinit dla widoków rejestru 32/64-bit, user/common Startup, usług, sterowników i zadań, ograniczając liczbę wpisów i wstrzymując wnioskowanie przy błędzie źródła. Wszystkie trzy odmiany rejestru uruchamiania są teraz objęte.
   3. Dodać opt-in ustawienie, cykl baseline → delta, pauzę, status diagnostyczny i bounded queue.
   4. Zastosować wyjaśnialne heurystyki dla ścieżek Temporary/Downloads/Public; zdarzenia mają być informacyjne, dopóki nie ma wiarygodnej reputacji.
   5. Zintegrować lokalne zdarzenia bez Enterprise sync; nie zapisywać surowej komendy, argumentów ani pełnej wartości rejestru.
   6. Dodać testy baseline, add/change/remove, duplikatów, pauzy, błędu źródła, limitu i redakcji, następnie Windows live read-only smoke.
   7. Zaktualizować UI, diagnostykę, changelog, macierz i ten plan po pełnym buildzie.
7. **Zmiany w plikach:** spodziewane `src/Sentinel.Engine/WindowsPersistenceSnapshotMonitor.cs`, `Program.cs`, ustawienia w `src/Sentinel.Core/Models.cs`, UI `desktop/src/main.tsx`, testy Engine, a jeśli trwały baseline okaże się potrzebny — `LocalStore.cs` i migracja SQLite; lista ma być aktualizowana po wdrożeniu.
8. **Bezpieczeństwo i prywatność:** tylko opt-in; źródła systemowe są odczytywane bez zapisu, komendy, argumenty, nazwy usług/zadań i surowe wartości nie trafiają do bazy, diagnostyki, eksportu ani Enterprise. Dla Winlogon i Policies do bazy trafiają tylko hash wartości; dla usług/sterowników hash obejmuje wybrane wartości startu, typu, konta oraz ścieżek obrazu/biblioteki. Najpierw ustanowić baseline, by istniejące komponenty nie powodowały zalewu alertów. Nie uruchamiać ani nie zmieniać wskazanych plików/wartości.
9. **Testy:** źródła wstrzykiwane; kontrolowane wpisy syntetyczne; test ścieżek reparse point; limity wielkości/liczby; redakcja; testy włącz/wyłącz/pauza; migracje v24→v28, v26→v28 i v27→v28, backup/restore; live read-only enumeracja rejestru Windows z jawnie ustawioną zmienną środowiskową. Testy nie tworzą, nie zmieniają ani nie uruchamiają prawdziwych zadań Windows.
10. **Kryteria akceptacji:** domyślnie wyłączone; baseline bez zdarzeń; zmiana syntetyczna tworzy jeden lokalny rekord; wyłączenie/pauza zatrzymuje obserwację; odmowa/awaria źródła jest diagnozowalna i nie usuwa starego baseline'u; surowa komenda/XML/nazwa nie jest zapisywana/eksportowana/synchronizowana; UI wyjaśnia zależność dostępu do zadań.
11. **Ryzyka i ograniczenia:** nie obejmuje wszystkich polityk logowania ani wszystkich ścieżek trwałości; polling może pominąć krótkotrwałe wpisy lub zmianę dodaną i cofniętą podczas zamknięcia; odmowa dostępu do rejestru zachowuje baseline źródła rejestru, a odmowa `schtasks` pomija zmiany zadań do przywrócenia dostępu; limit 1024 łącznych wpisów może zawiesić próbkę na urządzeniu z dużą liczbą komponentów; heurystyka ścieżek może dawać false positives.
12. **Status realizacji:** `IN_PROGRESS` — monitor obejmuje Run/RunOnce, Policies Explorer Run, wybrane wartości Winlogon Shell/Userinit, foldery Startup, zadania, usługi i sterowniki. Dla Policies i Winlogon zapisuje zredagowany skrót wartości, a nie nazwę programu ani polecenie; zgłasza ogólny lokalny alert. Limit wspólny wynosi 1024. Testy monitora 24/24; pełna `scripts/build-user.ps1 -Installer` PASS (.NET 333/333 bez pominięć, ewaluatory, plany 13/13, Engine IPC/DNS/TCP/UDP, Electron 16/16, `npm audit` 0, UI i installer self-test). Lokalny artefakt testowy v0.15.38 ma 281365881 B i SHA-256 `8A520ED7D699D9A6478F12382EAB8EB9565528F98D58C3FCB9B3BBB6911E2BA2`; nie uruchomiono go w integration test ani GUI. Migracja SQLite v27→v28 zachowuje istniejący baseline i dopuszcza nowe źródła. Jawnie włączone live read-only testy rejestru usług/sterowników i Run/Winlogon przeszły po 1/1 w sesji Windows 2026-10-23; dla Run/Winlogon użyto tylko tymczasowej bazy, rejestru nie zmieniano. GUI, restart monitora i dostęp na zwykłym profilu Windows wymagają walidacji interaktywnej. Pozostają AppInit_DLLs, rozszerzenia powłoki, inne mechanizmy trwałości i możliwość pominięcia zmiany w całości podczas zamknięcia.
