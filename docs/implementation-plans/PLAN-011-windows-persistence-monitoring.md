# PLAN-011 — monitorowanie trwałości Windows

1. **Cel:** po osobnym, jawnym włączeniu wykrywać zmiany w rejestrze Run/RunOnce użytkownika i maszyny, folderach Startup oraz zaplanowanych zadaniach Windows, bez udawania pełnego monitoringu wszystkich mechanizmów trwałości.
2. **Stan obecny:** Electron rejestruje własne uruchamianie z Windows przez `app.setLoginItemSettings`. Audyt read-only 2026-10-22 potwierdził dostęp do HKCU `Run` (0 wpisów), HKLM `Run` i `WOW6432Node\Run` (3 i 8 wartości) oraz user/common Startup (1 i 2 elementy); nie odczytywano ani nie wypisywano nazw ani komend. Pierwotne WMI i COM były niedostępne w ograniczonym środowisku. Późniejszy odczyt poza sandboxem przez `schtasks /query /xml` bez uruchamiania zadań poprawnie sparsował 175 wpisów; standardowy sandbox zwrócił kod 1. Dziennik Task Scheduler pozostaje wyłączony i nie był modyfikowany.
3. **Stan implementacji:** opt-in monitor działa dla HKCU/HKLM `Run`/`RunOnce` (widoki 32/64-bit), bezpośrednich plików w Startup użytkownika/wspólnym Startup i Scheduled Tasks przez `schtasks /query /xml`. Dla zadań zapisuje tylko SHA-256 hashowanego URI i definicji; surowy XML, nazwy, argumenty i ścieżki pozostają w pamięci procesu. Snapshot działa co ≥30 s, ma limit 256 łącznych wpisów, 32 lokalne zdarzenia na próbkę, timeout 10 s oraz limit wyniku 8 MiB. SQLite v21 przechowuje osobny stan inicjalizacji baseline'u zadań; pierwszy dostęp tworzy cichy baseline. Jeśli źródło jest niedostępne, poprzednie zadania zostają w baseline i pozostałe źródła nadal są porównywane. Zdarzenia są lokalne i nie trafiają do Enterprise. Testy monitora 15/15 oraz live read-only parsowanie 175 zadań PASS.
4. **Decyzje architektoniczne:** monitor pozostaje wyłączony domyślnie. Nie włączać kanałów Event Log ani nie zmieniać rejestru/polityk/zadań systemowych. Odczyt zadań jest best-effort: standardowy proces może otrzymać odmowę; UI pokazuje stan, zachowuje baseline i kontynuuje pozostałe źródła. Użyć ograniczonego polling'u i cichego baseline'u, aby nie tworzyć alertów dla stanu zastanego przy włączeniu.
5. **Zależności:** nowe pole ustawień w Engine/UI; bez dodatkowego pakietu; testy Windows mogą używać wstrzykiwanego źródła i tymczasowego katalogu, bez zapisu do prawdziwych kluczy rejestru.
6. **Etapy implementacji:**
   1. Zdefiniować niejawny, stabilny klucz porównawczy źródła/wartości i typowane rekordy snapshotu.
   2. Dodać czytniki HKCU/HKLM Run/RunOnce dla widoków rejestru 32/64-bit oraz user/common Startup, ograniczając liczbę wpisów i wstrzymując wnioskowanie przy błędzie źródła.
   3. Dodać opt-in ustawienie, cykl baseline → delta, pauzę, status diagnostyczny i bounded queue.
   4. Zastosować wyjaśnialne heurystyki dla ścieżek Temporary/Downloads/Public; zdarzenia mają być informacyjne, dopóki nie ma wiarygodnej reputacji.
   5. Zintegrować lokalne zdarzenia bez Enterprise sync; nie zapisywać surowej komendy, argumentów ani pełnej wartości rejestru.
   6. Dodać testy baseline, add/change/remove, duplikatów, pauzy, błędu źródła, limitu i redakcji, następnie Windows live read-only smoke.
   7. Zaktualizować UI, diagnostykę, changelog, macierz i ten plan po pełnym buildzie.
7. **Zmiany w plikach:** spodziewane `src/Sentinel.Engine/WindowsPersistenceSnapshotMonitor.cs`, `Program.cs`, ustawienia w `src/Sentinel.Core/Models.cs`, UI `desktop/src/main.tsx`, testy Engine, a jeśli trwały baseline okaże się potrzebny — `LocalStore.cs` i migracja SQLite; lista ma być aktualizowana po wdrożeniu.
8. **Bezpieczeństwo i prywatność:** tylko opt-in; źródła systemowe są odczytywane bez zapisu, komendy, argumenty i surowe wartości nie trafiają do bazy, diagnostyki, eksportu ani Enterprise. Najpierw ustanowić baseline, by istniejące aplikacje nie powodowały zalewu alertów. Nie uruchamiać ani nie zmieniać wskazanych plików/wartości.
9. **Testy:** źródła wstrzykiwane; kontrolowane wpisy syntetyczne; test ścieżek reparse point; limity wielkości/liczby; redakcja; testy włącz/wyłącz/pauza; migracja v20→v21 i backup/restore; live read-only parser Windows z jawnie ustawioną zmienną środowiskową. Testy nie tworzą, nie zmieniają ani nie uruchamiają prawdziwych zadań Windows.
10. **Kryteria akceptacji:** domyślnie wyłączone; baseline bez zdarzeń; zmiana syntetyczna tworzy jeden lokalny rekord; wyłączenie/pauza zatrzymuje obserwację; odmowa/awaria źródła jest diagnozowalna i nie usuwa starego baseline'u; surowa komenda/XML/nazwa nie jest zapisywana/eksportowana/synchronizowana; UI wyjaśnia zależność dostępu do zadań.
11. **Ryzyka i ograniczenia:** nie obejmuje usług, sterowników, polityk logowania ani wszystkich ścieżek `Run`; polling może pominąć krótkotrwałe wpisy lub zmianę dodaną i cofniętą podczas zamknięcia; odmowa dostępu do `schtasks` pomija zmiany zadań do przywrócenia dostępu; limit 256 łącznych wpisów może zawiesić próbkę na urządzeniu z dużą liczbą zadań; heurystyka ścieżek może dawać false positives.
12. **Status realizacji:** `IN_PROGRESS` — czytniki, baseline, delta, UI i testy wdrożone; monitor 15/15, live read-only przepływ odczyt→parser→tymczasowa baza dla 175 zadań PASS; SQLite v21 migracja i redakcja przechodzą testy. Najnowsza pełna bramka po SQLite v22 PASS (.NET 277/277, Electron 14/14, `npm audit` 0, UI i installer self-test); wcześniejsza bramka v21 była .NET 254/254. GUI i rzeczywisty cykl włączenia monitorowania wymagają jeszcze walidacji interaktywnej. Nie wykrywa zmian dodanych i cofniętych w całości podczas zamknięcia aplikacji.
