# PLAN-011 — monitorowanie trwałości Windows

1. **Cel:** po osobnym, jawnym włączeniu wykrywać dodanie lub zmianę wpisów autostartu bieżącego użytkownika, bez udawania pełnego monitoringu wszystkich mechanizmów trwałości Windows.
2. **Stan obecny:** Electron rejestruje własne uruchamianie z Windows przez `app.setLoginItemSettings`, lecz produkt nie obserwuje zmian innych wpisów. Audyt read-only 2026-10-22 potwierdził dostęp do HKCU `Run` (0 wpisów) oraz folderu Startup użytkownika (1 element); klucz `RunOnce` nie istniał. W tej sesji HKLM `Run` i `WOW6432Node\Run` były czytelne (3 i 8 wartości), a wspólny Startup zawierał 2 elementy. Nie odczytywano ani nie wypisywano nazw i komend wpisów. Dziennik `Microsoft-Windows-TaskScheduler/Operational` jest dostępny, ale wyłączony; usługa działa. `Get-ScheduledTask` zakończył się `CimException`, kategorią `PermissionDenied`, HRESULT `0x80041003`; `schtasks /query` nie uzyskał listy.
3. **Stan implementacji:** opt-in monitor działa dla HKCU `Run`/`RunOnce` i bezpośrednich plików w Startup bieżącego użytkownika. Snapshot co najmniej co 30 s, cichy baseline, maks. 256 elementów i 32 lokalne zdarzenia na próbkę. Zdarzenia nie przechowują komendy ani pełnej ścieżki i nie trafiają do Enterprise. UI wyjaśnia zakres oraz ograniczenie braku monitorowania przy zamkniętej aplikacji. Siedem testów jednostkowych przechodzi; Engine IPC sprawdził read-only baseline profilu bez zmiany systemu.
4. **Decyzje architektoniczne:** rozpocząć od HKCU `Run`/`RunOnce` i folderu Startup użytkownika, z wyłączonym domyślnym ustawieniem. Nie włączać kanałów Event Log ani nie zmieniać rejestru/polityk systemowych. Nie wymagać administratora; HKLM i zadania systemowe pozostają poza pierwszym zakresem, dopóki nie ma bezpiecznego, jawnego sposobu dostępu. Użyć wykrywania zmian lub ograniczonego polling'u z debounce i bazą, która nie wywołuje alertów dla stanu zastanego przy włączeniu.
5. **Zależności:** nowe pole ustawień w Engine/UI; bez dodatkowego pakietu; testy Windows mogą używać wstrzykiwanego źródła i tymczasowego katalogu, bez zapisu do prawdziwych kluczy rejestru.
6. **Etapy implementacji:**
   1. Zdefiniować niejawny, stabilny klucz porównawczy źródła/wartości i typowane rekordy snapshotu.
   2. Dodać czytnik HKCU Run/RunOnce oraz user Startup, ograniczając liczbę wpisów i obsługując brak/odmowę dostępu.
   3. Dodać opt-in ustawienie, cykl baseline → delta, pauzę, status diagnostyczny i bounded queue.
   4. Zastosować wyjaśnialne heurystyki dla ścieżek Temporary/Downloads/Public; zdarzenia mają być informacyjne, dopóki nie ma wiarygodnej reputacji.
   5. Zintegrować lokalne zdarzenia bez Enterprise sync; nie zapisywać surowej komendy, argumentów ani pełnej wartości rejestru.
   6. Dodać testy baseline, add/change/remove, duplikatów, pauzy, błędu źródła, limitu i redakcji, następnie Windows live read-only smoke.
   7. Zaktualizować UI, diagnostykę, changelog, macierz i ten plan po pełnym buildzie.
7. **Zmiany w plikach:** spodziewane `src/Sentinel.Engine/WindowsPersistenceSnapshotMonitor.cs`, `Program.cs`, ustawienia w `src/Sentinel.Core/Models.cs`, UI `desktop/src/main.tsx`, testy Engine, a jeśli trwały baseline okaże się potrzebny — `LocalStore.cs` i migracja SQLite; lista ma być aktualizowana po wdrożeniu.
8. **Bezpieczeństwo i prywatność:** tylko opt-in i dane bieżącego użytkownika; komendy, argumenty i surowe wartości nie trafiają do bazy, diagnostyki, eksportu ani Enterprise. Najpierw ustanowić baseline, by istniejące aplikacje nie powodowały zalewu alertów. Nie uruchamiać ani nie zmieniać wskazanych plików/wartości.
9. **Testy:** źródło wstrzykiwane; kontrolowane wpisy syntetyczne; test ścieżek reparse point; limity wielkości/liczby; brak ujawnienia wartości w zdarzeniu i eksporcie; testy włącz/wyłącz/pauza; Windows read-only dla dostępności HKCU i folderu Startup. Nie testować zmian w prawdziwym HKCU/HKLM.
10. **Kryteria akceptacji:** domyślnie wyłączone; baseline bez zdarzeń; zmiana syntetyczna tworzy jeden lokalny rekord; wyłączenie/pauza zatrzymuje obserwację; odmowa/awaria źródła jest diagnozowalna; surowa komenda nie jest zapisywana/eksportowana/synchronizowana; ograniczenia HKLM i Scheduled Tasks są widoczne w UI/dokumentacji.
11. **Ryzyka i ograniczenia:** wyłącznie bieżący użytkownik; nie obejmuje usług, sterowników, WMI/COM, zadań zaplanowanych, polityk logowania ani wszystkich ścieżek `Run`; polling może pominąć krótkotrwałe wpisy; ścieżki mogą być aliasowane przez zmienne środowiskowe/reparse points; heuristiczne lokalizacje mogą dać false positives.
12. **Status realizacji:** `IN_PROGRESS` — kroki 1–5 oraz testy syntetyczne wdrożone; testy jednostkowe 7/7 przechodzą. Pełna bramka instalatora trwa. Nie przetestowano zmiany rzeczywistego wpisu autostartu, HKLM ani Scheduled Tasks; nie wykrywa zmian podczas zamknięcia aplikacji.
