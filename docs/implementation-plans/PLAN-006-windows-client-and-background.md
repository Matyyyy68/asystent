# PLAN-006 — klient Windows i działanie w tle

**F13 — obsługa nieudanego startu silnika (2026-10-25):** inicjalizacja i główny przebieg `Sentinel.Engine` mają granicę obsługi wyjątków zarządzanych. Zamiast nieobsłużonego CLR crash proces zapisuje wyłącznie `SENTINEL_ENGINE_FATAL type=<typ>` do stderr i kończy kodem 1; desktopowy supervisor wyciąga typ, redaguje resztę i zapisuje bezpieczny rekord diagnostyczny. Procesowy test regresyjny wymusza błąd przez konflikt pliku/katalogu danych i sprawdza kod 1, brak `Unhandled exception` i brak ścieżki. Parser czeka na pełną linię stderr; dodatkowy test dzieli marker między dwa fragmenty i potwierdza, że nazwa typu jest pełna. Pełny Release .NET 387 PASS + 2 platformowe SKIP, Electron 47/47, pełna bramka offline PASS. Nie dowodzi to przyczyny wcześniejszego błędu `dotnet.exe` i nie obejmuje wyjątku spoza głównego przebiegu Engine; pełne GUI oraz restart systemu pozostają otwarte.

**F13 — backoff odporności restartu (2026-10-24):** poprawiono reset licznika retry: udana odpowiedź nie zeruje już wykładniczego opóźnienia przy krótkotrwałym silniku. Opóźnienie rośnie 1→2→4 s i dochodzi do limitu 30 s; reset następuje po co najmniej 60 s stabilnego działania. Trzy testy regresyjne potwierdzają narastanie, limit 30 s i reset; desktop 36/36; osobny test potwierdza, że błąd spawn nie dziedziczy stderr poprzedniego procesu. Nie testowano restartu Windows ani długiego soak.

**F13 — typ wyjątku i kod Windows w diagnostyce (2026-10-24):** ekran diagnostyki pokazuje przechwycony, zredagowany typ wyjątku .NET oraz ostatni kod zakończenia w formie dziesiętnej i szesnastkowej; formatter obsługuje signed/unsigned DWORD. Po restarcie pobiera najnowszy bezpieczny wpis z lokalnego dziennika 64 awarii. Testy desktop 36/36, `tsc --noEmit` i Vite production build PASS. Nie pokazuje komunikatu wyjątku, stosu ani ścieżek; zachowanie widoku w uruchomionej aplikacji Windows pozostaje do sprawdzenia.

1. **Cel:** zapewnić czytelny stan modułów, bezpieczny tray/autostart i diagnozowalne błędy.
2. **Stan obecny:** Electron ma single-instance lock, tray, hide-on-close, autostart API i cykliczny DNS. Diagnostyka pokazuje working set, pamięć prywatną, czas CPU, stan lifecycle, ograniczony kod zakończenia, flagę stderr i opcjonalną, walidowaną nazwę typu nieobsłużonego wyjątku .NET z prefiksu stderr silnika. Nie zapisuje treści wyjątku ani ścieżek. Ostatnie 64 awarie są zapisywane lokalnie w `%LOCALAPPDATA%/Sentinel AI/Logs/engine-lifecycle.jsonl` z czasem, ograniczonym kodem zakończenia, flagą stderr i filtrowanym typem wyjątku; eksport diagnostyczny dołącza te wpisy na jawne żądanie. `EngineClient` ponawia uruchomienie silnika z wykładniczym opóźnieniem do 30 s po błędzie startu, wyjściu procesu, błędzie stdin, niepoprawnej odpowiedzi lub timeout żądania (45 s); przy timeout kończy zawieszony proces, odrzuca oczekujące IPC i restartuje silnik. Retry jest czyszczone przy zamknięciu. Build/self-test działa; realny restart Windows i GUI nie były walidowane.
3. **Braki:** typ wyjątku może wskazać klasę awarii, ale nie ujawnia komunikatu ani przyczyny; awarie bez standardowego prefiksu .NET nadal pokażą tylko kod i flagę stderr. Dziennik zachowuje do 64 ostatnich awarii również po restarcie aplikacji. Brak service recovery/heartbeat oraz testów po restarcie Windows. Pakiet eksportu zawiera allowlistowany stan lifecycle, do 64 zredagowanych wpisów, ograniczony kod zakończenia, flagę stderr i filtrowaną nazwę typu; bez treści stderr ani ścieżek.
4. **Decyzje:** pozostawić desktop per-user bez Windows service na tym etapie; logować kody błędów z redakcją; nie dublować autostartu rejestrem i Electronem.
5. **Zależności:** schema event, installer, Windows profile.
6. **Etapy:** (a) structured diagnostic errors — częściowo, stan i kod exit są widoczne, ale bez opisu przyczyny; (b) retry/backoff engine — wdrożone i testowane; (c) zweryfikować autostart w installed app; (d) accessibility + error states; (e) soak/resource tests; (f) eksport lifecycle z allowlistą i filtrowaniem kodu — wdrożone i objęte testem IPC.
7. **Pliki:** Electron main, Engine, UI, validation docs, installer smoke tests.
8. **Prywatność:** log bez treści/URL; state/tray bez szczegółowych nawyków.
9. **Testy:** Testy desktop 36/36 obejmują odpowiedź IPC po starcie, restart po wyjściu i timeout, zabicie zawieszonego silnika, odrzucenie oczekujących żądań, zatrzymanie retry przy zamknięciu oraz brak ujawniania stderr i czyszczenie metadanych każdej próby przed spawn; dodatkowe regresje sprawdzają backoff 1→2→4 s przy krótkich uruchomieniach i reset po stabilnej minucie; regresja potwierdza, że typ wyjątku z kolejnej awarii zastępuje poprzedni bez komunikatu/ścieżki. Test Engine IPC sprawdza eksport allowlistowanego lifecycle, filtrowanie kodu zakończenia i odrzucenie nadmiarowego tekstu wyjątku. Pozostają realny crash/restart GUI, autostart true/false po reboot, tray/minimize/exit, dostępność i resource profile. Bieżący 30 s profil jednej sesji: working set 43,4–45,3 MiB, średnie CPU 0,124% po normalizacji do wszystkich logicznych procesorów; nie zastępuje soak testu.
10. **Akceptacja:** błędy w UI/logu, stan „ready” zgodny z procesem, exit zatrzymuje child, brak podwójnej instancji.
11. **Ryzyka:** polityki Windows blokują autostart/notify; test wymaga sesji GUI/restartu.
**Walidacja diagnostyki (2026-10-22):** .NET 233/233, Engine IPC, Windows DNS/TCP/UDP, desktop 14/14, `npm audit` 0, UI production build i installer self-test PASS. Lokalny instalator v0.15.38 nie został opublikowany; SHA-256 `D307A37809F1009A68E0E4C0BD45B90EA5218DEF6F9A80AE69E4E0092DCA382D`.

Rzeczywisty restart Windows, autostart zainstalowanego klienta, pełny cykl GUI, dostępność oraz długotrwały soak nadal wymagają sprawdzenia.
13. **Rozszerzenie — stan przy starcie (2026-10-23):** listener nawigacji czeka na odczyt zapisanej konfiguracji `integrationEnabled`, więc wcześniejsze wyłączenie przeglądarkowej integracji obowiązuje od pierwszej nawigacji po starcie service workera; przy błędzie odczytu pozostaje wyłączona. Testy desktop odtwarzają opóźnione `false` i błąd storage; zestaw 16/16 i Release klienta 301/301 PASS. Użytkownik zatwierdził aktualny E2E w osobnym profilu Chrome dla `.test`, ale CUA nie udostępniło Chrome ani okna natywnego; próba utworzenia karty w przeglądarce Chrome zakończyła się `Browser is not available: chrome`. Nie załadowano rozszerzenia i nie zmieniono HKCU. Ten bieżący E2E pozostaje niewykonany z powodu braku obsługi Chrome w dostępnym interfejsie.
14. **Chrome E2E — ponowiona próba (2026-10-23):** pierwsze uruchomienie miało pustą listę argumentów z powodu błędu skryptu i otworzyło zwykłą nową kartę. Drugie uruchomienie poprawnie utworzyło odizolowany profil oraz port CDP, ale Chrome 155 zignorował `--load-extension`, a CUA odmówiło odczytu URL okna i dalszej obsługi `chrome://extensions`.
