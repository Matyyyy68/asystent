# PLAN-006 — klient Windows i działanie w tle

1. **Cel:** zapewnić czytelny stan modułów, bezpieczny tray/autostart i diagnozowalne błędy.
2. **Stan obecny:** Electron ma single-instance lock, tray, hide-on-close, autostart API i cykliczny DNS. Diagnostyka pokazuje working set, pamięć prywatną, czas CPU, stan lifecycle, ograniczony kod zakończenia, flagę stderr i opcjonalną, walidowaną nazwę typu nieobsłużonego wyjątku .NET z prefiksu stderr silnika. Nie zapisuje treści wyjątku ani ścieżek. Ostatnie 64 awarie są zapisywane lokalnie w `%LOCALAPPDATA%/Sentinel AI/Logs/engine-lifecycle.jsonl` z czasem, ograniczonym kodem zakończenia, flagą stderr i filtrowanym typem wyjątku; eksport diagnostyczny dołącza te wpisy na jawne żądanie. `EngineClient` ponawia uruchomienie silnika z wykładniczym opóźnieniem do 30 s po błędzie startu, wyjściu procesu, błędzie stdin, niepoprawnej odpowiedzi lub timeout żądania (45 s); przy timeout kończy zawieszony proces, odrzuca oczekujące IPC i restartuje silnik. Retry jest czyszczone przy zamknięciu. Build/self-test działa; realny restart Windows i GUI nie były walidowane.
3. **Braki:** typ wyjątku może wskazać klasę awarii, ale nie ujawnia komunikatu ani przyczyny; awarie bez standardowego prefiksu .NET nadal pokażą tylko kod i flagę stderr. Dziennik zachowuje do 64 ostatnich awarii również po restarcie aplikacji. Brak service recovery/heartbeat oraz testów po restarcie Windows. Pakiet eksportu zawiera allowlistowany stan lifecycle, do 64 zredagowanych wpisów, ograniczony kod zakończenia, flagę stderr i filtrowaną nazwę typu; bez treści stderr ani ścieżek.
4. **Decyzje:** pozostawić desktop per-user bez Windows service na tym etapie; logować kody błędów z redakcją; nie dublować autostartu rejestrem i Electronem.
5. **Zależności:** schema event, installer, Windows profile.
6. **Etapy:** (a) structured diagnostic errors — częściowo, stan i kod exit są widoczne, ale bez opisu przyczyny; (b) retry/backoff engine — wdrożone i testowane; (c) zweryfikować autostart w installed app; (d) accessibility + error states; (e) soak/resource tests; (f) eksport lifecycle z allowlistą i filtrowaniem kodu — wdrożone i objęte testem IPC.
7. **Pliki:** Electron main, Engine, UI, validation docs, installer smoke tests.
8. **Prywatność:** log bez treści/URL; state/tray bez szczegółowych nawyków.
9. **Testy:** Node testy 10/10 sprawdzają odpowiedź IPC po starcie, restart po wyjściu i timeout, zabicie zawieszonego silnika, odrzucenie oczekujących żądań, zatrzymanie retry przy zamknięciu oraz brak ujawniania stderr; regresja potwierdza, że typ wyjątku z kolejnej awarii zastępuje poprzedni bez komunikatu/ścieżki. Test Engine IPC sprawdza eksport allowlistowanego lifecycle, filtrowanie kodu zakończenia i odrzucenie nadmiarowego tekstu wyjątku. Pozostają realny crash/restart GUI, autostart true/false po reboot, tray/minimize/exit, dostępność i resource profile. Bieżący 30 s profil jednej sesji: working set 43,4–45,3 MiB, średnie CPU 0,124% po normalizacji do wszystkich logicznych procesorów; nie zastępuje soak testu.
10. **Akceptacja:** błędy w UI/logu, stan „ready” zgodny z procesem, exit zatrzymuje child, brak podwójnej instancji.
