# PLAN-006 — klient Windows i działanie w tle

1. **Cel:** zapewnić czytelny stan modułów, bezpieczny tray/autostart i diagnozowalne błędy.
2. **Stan obecny:** Electron ma single-instance lock, tray, hide-on-close, autostart API i cykliczny DNS. Diagnostyka pokazuje bieżący working set, pamięć prywatną, czas CPU, stan lifecycle procesu silnika, ograniczony kod zakończenia i tylko informację, czy stderr wystąpił. `EngineClient` ponawia uruchomienie silnika z wykładniczym opóźnieniem do 30 s po błędzie startu, wyjściu procesu, błędzie stdin, niepoprawnej odpowiedzi lub timeout żądania (45 s); przy timeout kończy zawieszony proces, odrzuca oczekujące IPC i restartuje silnik. Retry jest czyszczone przy zamknięciu. Surowe stderr nie jest logowane. Build/self-test działa; realny restart Windows i GUI nie były walidowane.
3. **Braki:** brak czytelnego opisu przyczyny awarii (diagnostyka podaje kod, nie treść wyjątku) i brak lifecycle Electron w eksportowanym pakiecie diagnostycznym; brak service recovery/heartbeat oraz testów po restarcie.
4. **Decyzje:** pozostawić desktop per-user bez Windows service na tym etapie; logować kody błędów z redakcją; nie dublować autostartu rejestrem i Electronem.
5. **Zależności:** schema event, installer, Windows profile.
6. **Etapy:** (a) structured diagnostic errors — częściowo, stan i kod exit są widoczne, ale bez opisu przyczyny; (b) retry/backoff engine — wdrożone i testowane; (c) zweryfikować autostart w installed app; (d) accessibility + error states; (e) soak/resource tests; (f) zdecydować, czy bezpiecznie dodać lifecycle do eksportu diagnostycznego.
7. **Pliki:** Electron main, Engine, UI, validation docs, installer smoke tests.
8. **Prywatność:** log bez treści/URL; state/tray bez szczegółowych nawyków.
9. **Testy:** Node testy 4/4 sprawdzają odpowiedź IPC po starcie, restart po wyjściu i timeout, zabicie zawieszonego silnika, odrzucenie oczekujących żądań, zatrzymanie retry przy zamknięciu oraz brak ujawniania stderr; są wykonywane przez `scripts/build-user.ps1`, a desktop lint/build PASS. Pozostają realny crash/restart GUI, autostart true/false po reboot, tray/minimize/exit, dostępność i resource profile. Bieżący 30 s profil jednej sesji: working set 43,4–45,3 MiB, średnie CPU 0,124% po normalizacji do wszystkich logicznych procesorów; nie zastępuje soak testu.
10. **Akceptacja:** błędy w UI/logu, stan „ready” zgodny z procesem, exit zatrzymuje child, brak podwójnej instancji.
11. **Ryzyka:** polityki Windows blokują autostart/notify; test wymaga sesji GUI/restartu.
12. **Status:** `IN_PROGRESS` — supervisor procesu silnika ma ograniczony retry/backoff, watchdog timeout, zamykanie child process i bezpieczną diagnostykę. Lokalna walidacja późniejszego kodu: desktop 6/6, Engine IPC, UI build i installer self-test PASS; Windows CI dla funkcjonalnego commita `79668a4` PASS (`39505227855`). Izolowane Chrome/Edge E2E potwierdzają tylko przetwarzanie fixture `.test`, nie instalację rozszerzenia/hosta w profilu codziennego użytkownika. Rzeczywisty restart Windows i autostart zainstalowanego klienta, ręczny cykl GUI, dostępność oraz długotrwały soak nadal wymagają sprawdzenia.
