# PLAN-010 — Enterprise API, agent i testy operacyjne

1. **Cel:** agent Enterprise działa w aktywnym kliencie jako jawnie sparowany wariant, z minimalnym eksportem metadanych i lokalnym egzekwowaniem polityki.
2. **Stan obecny:** backend ma SQLite/RBAC/sesje/polityki/audyt/consent-gated Ollama/FTS5; testy serwera 21/21 i API smoke PASS. Electron ma HTTPS pairing z jednorazowym invite, zgodę na metadane, token chroniony DPAPI CurrentUser, heartbeat, pobieranie polityki local i idempotentną kolejkę offline metadanych ograniczoną do 10 000 rekordów. Panel admina ma zatwierdzenie/odrzucenie i revoke urządzeń. Nowy live TLS E2E potwierdza klienta .NET z API na loopback.
3. **Braki:** harmonogram automatycznej rotacji; polityki poza local/10–300 s, restart/offline w pełnej aplikacji i podpisane aktualizacje.
4. **Decyzje:** pairing jest możliwy z ekranu ustawień po HTTPS i świadomej zgodzie. Zdarzenie Enterprise v1 wysyła tylko ID/czas/kategorię/ryzyko/kod reguły/schemaVersion/allowlistowane źródło/bezpieczną wersję reguły; treść, pełny URL, nazwa aplikacji i wyjaśnienie zostają lokalne. Wyłączenie zgody zatrzymuje również heartbeat i pobieranie polityki oraz usuwa oczekujące metadane. Klient nie udostępnia kontekstu do analizy serwerowej. Nieobsługiwany tryb polityki jest odrzucany z heartbeat `configuration_invalid`.
5. **Zależności:** certyfikat CA i wdrożony serwer Enterprise do walidacji zaufanego TLS, interaktywna sesja Windows z profilem DPAPI, Windows Server VM i certyfikat podpisu dla aktualizacji.
6. **Etapy:** (a) API schema i limity — wdrożone/testowane; (b) pairing, DPAPI i IPC consent — wdrożone, DPAPI test przeszedł poza sandboxem; (c) kolejka offline i deduplikacja — wdrożone/testy SQLite; (d) polityka lokalna/heartbeat — wdrożone; (e) wyłączenie zgody usuwa oczekujące metadane i blokuje wysłanie kolejki przywróconej z backupu — wdrożone/testowane; (f) live TLS E2E z approval, pairing, heartbeat, batch/dedupe, staged rotation i revoke — wdrożone/testowane na loopback z przypiętym certyfikatem tymczasowym; publiczny/zaufany certyfikat nie był użyty; (g) ręczna rotacja tokenu w aktywnym Engine/UI — wdrożona i objęta tym samym E2E; harmonogram rotacji, restart/offline i przeciążenie — pozostałe.
7. **Pliki:** `server/`, `src/Sentinel.Core/Enterprise/`, `src/Sentinel.Engine/Program.cs`, `desktop/src/main.tsx`, `desktop/electron/main.cjs`.
8. **Prywatność:** lokalny token DPAPI CurrentUser; kolejka metadanych w lokalnej SQLite tylko po zgodzie; brak tekstu, URL, nazw plików, promptów lub wyjaśnień; HTTPS obowiązkowe.
9. **Testy:** mock client, consent gate IPC, profil/queue gate i minimalny payload SQLite; .NET 202/202, serwer 21/21, live TLS E2E i API HTTP smoke PASS. E2E tworzy własny serwer, bazę, PFX i konto administratora; wszystko działa na loopback, a dane są usuwane po teście. UI production build i desktop 6/6 PASS po dodaniu jawnej rotacji. Do wykonania: offline/restart pełnej aplikacji, test certyfikatu zaufanego i test operacyjny serwera.
10. **Akceptacja:** pairing, approval, pobranie polityki, heartbeat, batch z deduplikacją, ręczne staged rotation i revoke przechodzą w live TLS E2E. Restart klienta, offline retry w pełnym kliencie i dowód prywatności na granicy procesu wymagają dalszego testu.
11. **Ryzyka:** dystrybucja certyfikatów, dostępność serwera, approval wymaga dostępu administratora organizacji, DPAPI zależne od profilu zalogowanego użytkownika.
12. **Status:** `IN_PROGRESS` — live E2E z API po TLS potwierdza pairing, approval, politykę, heartbeat, deduplikację, ręczną rotację z Engine/UI i revoke; klient zapisuje nowy token przez chroniony store przed promocją serwerową. Admin UI ma approval/revoke. Pozostaje test restart/offline całej aplikacji, certyfikat zaufany dla wdrożenia i ewentualny harmonogram rotacji.
