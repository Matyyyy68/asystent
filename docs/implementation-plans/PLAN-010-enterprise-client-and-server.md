# PLAN-010 — Enterprise API, agent i testy operacyjne

1. **Cel:** agent Enterprise działa w aktywnym kliencie jako jawnie sparowany wariant, z minimalnym eksportem metadanych i lokalnym egzekwowaniem polityki.
2. **Stan obecny:** backend ma SQLite/RBAC/sesje/polityki/audyt/consent-gated Ollama/FTS5; testy serwera 21/21 i API smoke PASS. Electron ma HTTPS pairing z jednorazowym invite, zgodę na metadane, token chroniony DPAPI CurrentUser, heartbeat, pobieranie polityki local i idempotentną kolejkę offline metadanych ograniczoną do 10 000 rekordów. Panel admina ma zatwierdzenie/odrzucenie i revoke urządzeń. Nowy live TLS E2E potwierdza klienta .NET z API na loopback.
3. **Braki:** harmonogram automatycznej rotacji; polityki poza local/10–300 s, udane wznowienie synchronizacji przez aktywny Engine po powrocie serwera, certyfikat zaufany dla wdrożenia i podpisane aktualizacje. Live TLS E2E teraz zatrzymuje i wznawia API, zachowuje batch po stronie testu i potwierdza udane ponowienie oraz deduplikację; tymczasowy certyfikat liścia jest przypięty wyłącznie w kliencie testowym. Test pełnego retry przez rzeczywisty proces Engine/DPAPI nie zmienia zaufania Windows i pozostaje nieweryfikowany.
4. **Decyzje:** pairing jest możliwy z ekranu ustawień po HTTPS i świadomej zgodzie. Zdarzenie Enterprise v1 wysyła tylko ID/czas/kategorię/ryzyko/kod reguły/schemaVersion/allowlistowane źródło/bezpieczną wersję reguły; treść, pełny URL, nazwa aplikacji i wyjaśnienie zostają lokalne. Wyłączenie zgody zatrzymuje również heartbeat i pobieranie polityki oraz usuwa oczekujące metadane. Klient nie udostępnia kontekstu do analizy serwerowej. Nieobsługiwany tryb polityki jest odrzucany z heartbeat `configuration_invalid`.
5. **Zależności:** certyfikat CA i wdrożony serwer Enterprise do walidacji zaufanego TLS, interaktywna sesja Windows z profilem DPAPI, Windows Server VM i certyfikat podpisu dla aktualizacji.
6. **Etapy:** (a) API schema i limity — wdrożone/testowane; (b) pairing, DPAPI i IPC consent — wdrożone, DPAPI test przeszedł poza sandboxem; (c) kolejka offline i deduplikacja — wdrożone/testy SQLite; (d) polityka lokalna/heartbeat — wdrożone; (e) wyłączenie zgody usuwa oczekujące metadane i blokuje wysłanie kolejki przywróconej z backupu — wdrożone/testowane; (f) live TLS E2E z approval, pairing, heartbeat, batch/dedupe, staged rotation i revoke — wdrożone/testowane na loopback z przypiętym certyfikatem tymczasowym; publiczny/zaufany certyfikat nie był użyty; (g) ręczna rotacja tokenu w aktywnym Engine/UI — wdrożona i objęta tym samym E2E; (h) rzeczywisty proces Engine: brak serwera daje `sync_failed`, kolejka i pairing przetrwają restart procesu, a cofnięcie zgody czyści kolejkę, blokuje sync i zachowuje historię lokalną — test Windows przeszedł z DPAPI w interaktywnej sesji; runner bez profilu DPAPI raportuje test jako pominięty; (i) live API po awarii: zachowanie batchu testowego przy przerwie, restart API z tą samą bazą i certyfikatem, retry oraz deduplikacja — PASS z certyfikatem przypiętym in-memory, bez instalacji w Windows; pomyślne wznowienie wewnątrz procesu Engine, harmonogram rotacji i przeciążenie pozostają.
7. **Pliki:** `server/`, `src/Sentinel.Core/Enterprise/`, `src/Sentinel.Engine/Program.cs`, `desktop/src/main.tsx`, `desktop/electron/main.cjs`.
8. **Prywatność:** lokalny token DPAPI CurrentUser; kolejka metadanych w lokalnej SQLite tylko po zgodzie; brak tekstu, URL, nazw plików, promptów lub wyjaśnień; HTTPS obowiązkowe.
9. **Testy:** mock client, consent gate IPC, profil/queue gate i minimalny payload SQLite; live TLS E2E tworzy własny serwer, bazę, PFX i konto administratora na loopback. E2E zatrzymuje serwer, potwierdza niepowodzenie requestu, uruchamia go ponownie, wysyła zachowany batch i sprawdza idempotencję. Klient testowy przypina tymczasowy certyfikat liścia w pamięci; test nie zmienia magazynów Windows. Serwer 21/21 PASS. Osobny test uruchamia prawdziwy proces Engine dwa razy z tym samym profilem DPAPI i bazą SQLite; Windows .NET pełny 207/207 PASS w interaktywnej sesji. Udane wznowienie kolejki w samym procesie Engine i test operacyjny serwera pozostają.
10. **Akceptacja:** pairing, approval, pobranie polityki, heartbeat, batch z deduplikacją, ręczne staged rotation, revoke oraz ponowienie batchu po restarcie API przechodzą w live TLS E2E. Test procesu potwierdza trwałość kolejki przez restart offline, odmowę wysyłki po cofnięciu zgody i zachowanie historii lokalnej; retry kolejki w samym procesie po powrocie serwera i dowód prywatności na granicy procesu wymagają dalszego testu.
11. **Ryzyka:** dystrybucja certyfikatów, dostępność serwera, approval wymaga dostępu administratora organizacji, DPAPI zależne od profilu zalogowanego użytkownika.
12. **Status:** `IN_PROGRESS` — live E2E z API po TLS potwierdza pairing, approval, politykę, heartbeat, deduplikację, ręczną rotację z Engine/UI, revoke oraz ponowienie retained batchu po zatrzymaniu i restarcie API. Klient testowy przypina certyfikat czasowy tylko w callbacku HTTP i nie instaluje go do zaufanych magazynów. Test rzeczywistego procesu Engine potwierdza zachowanie sparowania i kolejki po błędzie sieci oraz restarcie, a cofnięcie zgody zatrzymuje sync i usuwa kolejkę; retry wewnątrz tego procesu pozostaje. Pozostały test operacyjny serwera i ewentualny harmonogram rotacji.
