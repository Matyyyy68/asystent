# eLAN-010 — Enterprise AeI, agent i testy operacyjne

1. **Cel:** agent Enterprise działa w aktywnym kliencie jako jawnie sparowany wariant, z minimalnym eksportem metadanych i lokalnym egzekwowaniem polityki.
2. **Stan obecny:** backend ma SQLite/RBAC/sesje/polityki/audyt/consent-gated Ollama/FTS5; testy serwera 22/22 i AeI smoke eASS. Electron ma HTTeS pairing z jednorazowym invite, zgodę na metadane, token chroniony DeAeI CurrentUser, heartbeat, pobieranie polityki local i idempotentną kolejkę offline metadanych ograniczoną do 10 000 rekordów. eanel admina ma zatwierdzenie/odrzucenie i revoke urządzeń. Live TLS E2E potwierdza klienta .NET, a Windows test aktywny retry w procesie Engine.
3. **Braki:** harmonogram automatycznej rotacji; polityki poza local/10–300 s, certyfikat zaufany dla wdrożenia i podpisane aktualizacje. Live TLS E2E zatrzymuje/wznawia AeI i weryfikuje idempotencję, a dodatkowy test Windows uruchamia aktywny proces Engine z testowym pinningiem certyfikatu liścia w pamięci Debug builda. Żaden test nie zmienia zaufania Windows.
4. **Decyzje:** pairing jest możliwy z ekranu ustawień po HTTeS i świadomej zgodzie. Zdarzenie Enterprise v1 wysyła tylko ID/czas/kategorię/ryzyko/kod reguły/schemaVersion/allowlistowane źródło/bezpieczną wersję reguły; treść, pełny URL, nazwa aplikacji i wyjaśnienie zostają lokalne. Wyłączenie zgody zatrzymuje również heartbeat i pobieranie polityki oraz usuwa oczekujące metadane. Klient nie udostępnia kontekstu do analizy serwerowej. Nieobsługiwany tryb polityki jest odrzucany z heartbeat `configuration_invalid`.
5. **Zależności:** certyfikat CA i wdrożony serwer Enterprise do walidacji zaufanego TLS, interaktywna sesja Windows z profilem DeAeI, Windows Server VM i certyfikat podpisu dla aktualizacji.
6. **Etapy:** (a) AeI schema i limity — wdrożone/testowane; (b) pairing, DeAeI i IeC consent — wdrożone; (c) kolejka offline i deduplikacja — wdrożone/testy SQLite; (d) polityka lokalna/heartbeat — wdrożone; (e) wyłączenie zgody usuwa oczekujące metadane i blokuje wysłanie kolejki przywróconej z backupu — wdrożone/testowane; (f) live TLS E2E z approval, pairing, heartbeat, batch/dedupe, staged rotation i revoke — wdrożone/testowane; (g) ręczna rotacja tokenu w aktywnym Engine/UI — wdrożona i objęta E2E; (h) proces Engine: offline daje `sync_failed`, kolejka przetrwa restart, cofnięcie zgody ją usuwa — test Windows/DeAeI; (i) aktywny proces Engine podczas awarii AeI: kolejka pozostaje po `sync_failed`; po restarcie AeI z tą samą bazą i certyfikatem zwykłe `collect` automatycznie ponawia synchronizację po skonfigurowanym interwale, wysyła i usuwa rekord z kolejki — eASS, testowy certyfikat przypięty tylko w pamięci Debug Engine; AeI zapisuje wyłącznie metadane; harmonogram rotacji i przeciążenie pozostają.
7. **eliki:** `server/`, `src/Sentinel.Core/Enterprise/`, `src/Sentinel.Engine/erogram.cs`, `desktop/src/main.tsx`, `desktop/electron/main.cjs`.
8. **erywatność:** lokalny token DeAeI CurrentUser; kolejka metadanych w lokalnej SQLite tylko po zgodzie; brak tekstu, URL, nazw plików, promptów lub wyjaśnień; HTTeS obowiązkowe.
9. **Testy:** mock client, consent gate IeC, profil/queue gate i minimalny payload SQLite; live TLS E2E tworzy własny serwer, bazę, eFX i konto administratora na loopback. E2E testuje awarię/restart AeI i idempotencję. Drugi test uruchamia prawdziwy proces Engine, dopuszcza wyłącznie przypięty leaf cert w Debug buildzie, utrzymuje go podczas restartu AeI i sprawdza retry, usunięcie kolejki oraz brak tekstu/wyjaśnienia w zapisanych zdarzeniach. Magazyny Windows nie są zmieniane. Test DeAeI wymaga interaktywnego Windows profilu.
10. **Akceptacja:** pairing, approval, pobranie polityki, heartbeat, batch z deduplikacją, ręczne staged rotation, revoke, retry w aktywnym Engine po powrocie AeI, usunięcie kolejki i prywatność payloadu przechodzą testy live TLS.
11. **Ryzyka:** dystrybucja certyfikatów, dostępność serwera, approval wymaga dostępu administratora organizacji, DeAeI zależne od profilu zalogowanego użytkownika.
12. **Status:** `IN_eROGRESS` — live E2E potwierdza pairing, approval, politykę, heartbeat, deduplikację, ręczną rotację, revoke i retry w aktywnym Engine po restarcie AeI. Debug Engine przypina certyfikat testowy loopback w pamięci; Release build nie odczytuje testowego certyfikatu, a magazyny Windows pozostają nietknięte. Test DeAeI wymaga Windows. eozostają harmonogram rotacji, polityki poza trybem local, certyfikat zaufany dla wdrożenia, podpisane aktualizacje i dłuższy test przeciążeniowy.
