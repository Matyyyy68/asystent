# PLAN-002 — DNS i threat intelligence

1. **Cel:** jasno raportować świeżość źródeł i wiarygodne zdarzenia DNS/reputacji z mierzalnym opóźnieniem.
2. **Stan obecny:** użytkownik może jawnie kliknąć aktualizację stałego źródła `https://hole.cert.pl/domains/v2/domains.txt`; `DomainReputation.UpdateAsync` wymaga HTTPS do tego adresu, odrzuca przekierowania, ogranicza odpowiedź do 20 MiB, waliduje domeny i atomowo podmienia SQLite z możliwością rollbacku. W analizie nie wysyła URL-a ani domeny. Feed jest uznawany za wygasły po 48 h; brak aktualizacji w tle. `collect` odczytuje cache Windows przez `ipconfig /displaydns` co 15–300 s bez podnoszenia uprawnień. Test Windows-live wykonał cache read na zwykłym koncie; wcześniejszy `Get-DnsClientCache` zwracał `Access denied`.
3. **Braki:** brak odświeżania w tle i IP feedu; cache nie daje PID/timestamp zapytania. Parser i czytnik zdarzeń DNS Client Query Completed (3008) są wdrożone. Odczyt stanu kanału read-only 2026-10-23 potwierdził, że `Microsoft-Windows-DNS-Client/Operational` jest wyłączony; pełny odczyt zdarzeń można zweryfikować po jego świadomym włączeniu w kontrolowanym Windows. Konfiguracji kanału nie zmieniano.
4. **Decyzje:** aktualizacja CERT pozostaje jawnie inicjowana przez użytkownika, na stały endpoint bez parametrów zawierających analizowane adresy. Wpis CERT dopasowuje dokładną domenę oraz jej subdomeny wyłącznie na granicy etykiet; nie dopasowuje domeny nadrzędnej ani podobnie nazwanych hostów. Wpis równy publicznemu sufiksowi nie obejmuje jego tenantów. Odróżnić pustą bazę od świeżej; odczytywać DNS Client Operational tylko wtedy, gdy kanał jest już włączony; nie klasyfikować na podstawie wieku/nazwy. Nie zmieniać konfiguracji systemu ani nie wymagać admina po cichu.
5. **Zależności:** schemat zdarzeń, licencje źródeł, Internet tylko przy jawnej aktualizacji, Windows event source.
6. **Etapy:** (a) status feedu `never_loaded/active/stale/error` — wdrożone; (b) diagnostyka świeżości — wdrożona; (c) parser, HTTPS fetch na stały endpoint, limity, brak przekierowań i atomowy rollback — wdrożone; (d) parser 3008, bounded `wevtutil` reader, kursor SQLite v22, status wyłączonego kanału i brak zapisu `QueryResults` — wdrożone; (e) live smoke jawnego pobrania feedu i read-only odczytu kanału; (f) ewentualny IP feed wymaga osobnej decyzji źródła i warunków użycia.
7. **Pliki:** `DomainReputation.cs`, `Sentinel.Engine/Program.cs`, UI, testy reputation/engine, dokumentacja pokrycia.
8. **Prywatność:** feed pobierany z hosta CERT widzi IP klienta; analizowane URL nie są wysyłane; historia przechowuje tylko domenę wykrycia w ograniczonym przypadku.
9. **Testy:** 0/1/duplikat/niepoprawny feed, wygasły zegar, rollback, offline, kontrolowana domena `.test`, cache bez dopasowania i z nim, timeout/limity. Syntetyczne XML testy potwierdzają filtr dostawcy/kanału/EventID, kursor, odrzucenie IP/niepoprawnych nazw, limit i brak przechowania odpowiedzi; testy SQLite sprawdzają trwałość kursora i migrację v21→v22. Jawnie włączany test `SENTINEL_LIVE_CERT_FEED=1` weryfikuje aktualny publiczny feed na jego ściśle określonym endpointcie; osobne Windows-live testy potwierdziły odczyt cache oraz fallback wyłączonego kanału bez zmiany konfiguracji.
10. **Akceptacja:** pusty feed nie jest „aktualny”; awaria jawna; poprawna atomowość/rollback; udokumentowany udział cache/Operational i brak claimów pełnego DNS.
11. **Ryzyka:** DoH/DoT/VPN/krótki TTL omijają; ETW nie zobaczy resolvera aplikacyjnego/DoH; CERT jest ograniczonym źródłem.
